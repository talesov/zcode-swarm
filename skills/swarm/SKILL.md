# Swarm team development

One requirement in, a team out. The user states the requirement; the main session orchestrates the whole run itself with the Agent tool — coarse split, parallel background builders, independent review per card, rework on findings, mid-run expansion, the final gate — writing every state change to the run ledger (`.swarm/ledger.json`, managed by `scripts/swarm-ledger.mjs`) and surfacing progress as board cards.

## When

- `/swarm <需求>` or "让团队做/并行开发这个需求" → this skill.
- The work is one unit or a couple of independent lookups → plain `Agent` calls, not this.
- Same shape repeated across many inputs (audit N modules, migrate N files) → still fine here: each input becomes a task card.

## Flow (zero-checkpoint, event-driven)

1. **Role models + rework rounds (seconds, before any splitting)** — locate both scripts under the plugin cache (newest first): `swarm-config.mjs` for role models/rework rounds, `swarm-ledger.mjs` for run state. Run `node <swarm-config.mjs> show --json` and keep its `roles` array (`{ role, model, source }` for planner / architect / builder / reviewer / fixer) and `settings.rework_rounds` — they go into the ledger at init (`agent_models` + `rework_rounds`). There is no model preparation step: **the plugin does not configure models**, the host decides them (see [Models](#models)).
2. **Coarse split, fast** — planner discipline but coarse cards by default (a few minutes, not a deep dive): obvious scopes, per-card role, a gate command if the repo has one; evidence cap ≤6 files or the one named planning doc. Split in the main session (default — faster for small requirements) or spawn a `swarm-planner` background agent for large ones. Ask only when the requirement itself is ambiguous; if it points at an unnamed backlog ("待做的内容/TODO/继续完成"), ask for the concrete list or read only the one planning doc the user names — never roam the repo guessing what to do. Fewer than 2 cards → say so, use one Agent.
3. **Validate + init the ledger** — `node <swarm-config.mjs> validate --stdin` (card checks only: required fields, non-overlapping scopes; the script also refreshes the saved workflow) until it passes; never bypass, never a user stop. Then `node <swarm-ledger.mjs> init --stdin` with `{ "requirement", "cards", "gate" }` plus the optional run metadata `{ "agent_models": { "resolved": [...] }, "rework_rounds": N }` — `resolved` is the `roles` array from `show --json`, `rework_rounds` is `settings.rework_rounds` from the same output (stored on the ledger so the report card renders the model table and the rework cap follows the ledger). init accepts an empty `gate` (project with no test command). This creates `.swarm/ledger.json`, assigns the card ids that drive dispatch — then **optionally** `node <swarm-ledger.mjs> render board` and paste the emitted `::visualize` line into the reply (Gen UI card for chat-stream visibility), **and call the plugin's `swarm_board` tool** (an MCP tool, no arguments, read-only; returns a compact run summary — run/status/phase/progress/counts; it deliberately carries no `_meta.ui`, so the host does not re-render the panel page inline in chat). The MCP inline panel (board.html) now **auto-refreshes every 3 seconds** via postMessage to the MCP bridge — no manual render board needed for the panel itself. The persistent side panel 「团队看板」 is registered via the plugin's `ui.surfaces` (layout-dashboard icon, same mechanism as the official viewer plugins) — **open it once from the left sidebar icon**; full board data is at `resources/read ui://zcode-swarm/board.json`. The panel never reads the ledger itself — the `swarm-board` MCP server maps the ledger to a board resource (`ui://zcode-swarm/board.json`), `fs.watch`es the ledger and pushes updates, and the panel subscribes plus keeps a 5s fallback poll (2.5s when it has to read the resource directly, then a static snapshot with a manual-refresh button, and a 30s silent reconnect while disconnected). Chat cards remain — the panel is incremental, not a replacement; both render from the same ledger, and an empty state simply means this project has no run ledger yet.
3.5. **Architect (optional, on by default)** — when cards ≥3 or the requirement spans modules, spawn a `swarm-architect` background agent with the requirement + the **validated** card list; it returns a Markdown design doc (overall approach, key decisions, cross-card dependencies, risks, per-card advice). Persist it **after init** via `node <swarm-ledger.mjs> artifact design.md --stdin` (the command requires an existing ledger — never write it before init). Skip for 2 simple independent cards. Don't idle-wait: if builders are otherwise ready, dispatch dependency-free cards first and fold the architect's advice into those cards' next prompt (rework). Builders receive their card + the architect's per-card advice; reviewers also see the dependency/interface contract section.
4. **Parallel dispatch (Agent tool)** — for every pending card, spawn a background builder: `subagent_type: "swarm-builder"` (or `swarm-builder@zcode-swarm` to pin the source), `run_in_background: true`, prompt = the full card plus a required trailing result JSON block (`summary` / `files` / `spawns` — spawns lists genuinely new work found mid-build; a card's own small tail gets done in place, not reported). **Do not try to specify a model when dispatching**: the Agent tool has no per-spawn model parameter, and the host's per-agent setting (Settings → Subagents → ZCode Swarm) decides what each role actually runs on — editing the shared agent files to fake routing is useless and forbidden. Report what the ledger's `agent_models` says each role uses; if the user asks for a specific model, point them at the host setting. Immediately after each spawn: `node <swarm-ledger.mjs> update <id> --stdin` with `{ "state": "working", "agent_id": "<id>" }` — ledger first, next card second. **The script now auto-verifies agent_id existence** (checks `~/.zcode/cli/agents/*/metadata.json`); if the id doesn't exist (spawn was silently dropped), the write is rejected with exit 2 and a diagnostic — main session must re-spawn. Then `render board` again and report the dispatched cards (id/task/scope/role + model from `agent_models` + gate); tell the user they are free to go.
5. **Mid-run user message routing (FIRST thing on every user message while a run is active)** — when a user sends any message and a swarm run is in progress (ledger `status=running`), **do not respond directly**: first run `node <swarm-ledger.mjs> route "<the user's message>"` to get the current card states + scopes + a routing suggestion, then act on the route type:

   | Message type | Route |
   |---|---|
   | New work ("also do / add / 顺便") | `spawn` a new card → dispatch it |
   | Change affecting an in-flight card (working/reviewing/rework) | `bounce` to that card (capped 2/card) |
   | Change affecting a passed card | `spawn` a new card (passed cards are immutable) |
   | Cancel ("取消/算了/不要") | `update` the card to `failed` with `error: "用户取消"`, or `finish failed` |
   | Pause/stop ("暂停/停") | wait for in-flight cards to settle then `finish`; urgent → `finish failed` |
   | Unrelated to the run | answer normally + mention the swarm is still running |

   After routing, resume waiting for swarm notifications. **Never handle a mid-run message outside the swarm protocol when a run is active** — that breaks the team context.

6. **Event loop (notification → parse → ledger → review/rework/expand → board)** — never poll; background completions wake the main session, one at a time, routed by ledger state. Builder done → parse the result JSON (no JSON or a crashed task → treat the error text as a rework finding); `update <id>` with `result` + `state: "reviewing"`; triage `spawns`: worth doing → `node <swarm-ledger.mjs> spawn <parent-id> --stdin` a new card (same card shape as init's) and dispatch it like step 4, belongs to a running card's own tail → `node <swarm-ledger.mjs> bounce <target-card-id> --stdin` with `{ "text": "<extra instructions>", "source_card_id": "<card that reported the tail>" }` (`text` also accepts `title`/`summary`/`changes`; `source_card_id` is validated to exist and stored on the entry, becoming `card_id` on a deferred entry) — recorded on the target card's `bounces` (the rework prompt reads them from there), capped at **2 batches per card**; over-cap or late (target already passed/failed) is auto-converted to `deferred` (`超限（每卡最多 2 批）` / `迟到（目标卡已到终态）`) and lands in the report's 「遗留（Deferred）」/next-round list, so **never hand-write `finding --stdin` (with `"deferred": true`) for these**; a `pending` target is rejected (use `spawn` or `finding` instead), not worth doing → `node <swarm-ledger.mjs> finding --stdin` (`{ "text", "card_id?" }`) so it lands in the report. Then spawn a `swarm-reviewer` background agent (prompt = card + builder result; read-only review; answers PASS or FAIL with itemized findings). Review done → PASS: `update <id>` → `state: "passed"`. FAIL (under the rework-round cap): **two-step transition** — first `update <id>` with `{ "state": "rework", "review": {...} }` (the round increments on reviewing→rework), then re-spawn the builder with the findings appended and `update` → `{ "state": "working" }` (a direct reviewing→working write is rejected by the state machine). At the cap → `state: "failed"`. After **every** state change: **optionally** `node <swarm-ledger.mjs> render board` and paste the emitted `::visualize` line into the reply (Gen UI card for chat-stream visibility). **The MCP inline panel auto-refreshes every 3 seconds** via postMessage to the MCP bridge; the side panel needs no further calls, it follows the board resource on its own (server-side `fs.watch` push + 5s fallback poll) once opened from the left sidebar icon. Fixer completions (step 6) re-enter this loop and route to re-running the gate.
7. **Gate (direct Bash)** — when every card is terminal (passed/failed), the main session runs the gate command itself via Bash; an empty gate skips verification entirely (straight to `finish completed`). Green → `node <swarm-ledger.mjs> gate pass` then `finish completed`. Red → `node <swarm-ledger.mjs> gate fail`, spawn a `swarm-fixer` background agent with the full gate output plus the failing cards' info; on its notification record `node <swarm-ledger.mjs> fixer --stdin` (`{ "summary", "files" }`) and re-run the gate; fixer rounds cap = rework_rounds, then `finish failed`. Without these ledger calls the board and report keep showing the gate as "not run".
8. **Report** — `node <swarm-ledger.mjs> report` prints the markdown report (per-card final states, rework rounds, expansion triage, gate outcome, role model table). Then `node <swarm-ledger.mjs> render report` and paste the `::visualize` line — the model table comes from the ledger's `agent_models` (`resolved` entries written at init). Deliver markdown + card as the final reply. Disclose that content changes in untracked files are invisible to the platform's diffing; keep `.swarm/ledger.json` after the run for audit.
9. **Resume / abandon** — `/swarm resume` continues an interrupted run from the ledger (re-spawn builders for cards stuck in `working` — the originals died with the session — then re-enter the event loop; call `render board` once to bring the chat card back; reopen the side panel from the left sidebar icon, since a session restart usually closes it); `/swarm abandon` marks cards still in progress `failed` and finishes the run (`finish failed`) so the ledger archives cleanly. The SessionStart hook prints the recovery hint automatically when a running ledger exists.

The user touches the requirement and the final report; everything in between is the main session reacting to completion notifications — **plus the active-poll safety net below, because notifications can be lost**.

## Collecting results: notifications + the active-poll safety net

 Never wait on notifications alone:

1. **Record agent-ids at dispatch** — right after each spawn, write the builder's agent-id onto its card: `node <swarm-ledger.mjs> update <id> --stdin` with `{"agent_id": "<id>"}` (non-string values are ignored).
2. **Active poll at 30 min (script-managed, not cron-driven)** — the `watchdog` command now **self-registers a timer** on first call (writes a marker file to temp dir) and **auto-cleans it on finish**. No manual `CronCreate`/`CronDelete` needed. When the timer fires, run `node <swarm-ledger.mjs> watchdog` — it prints one line per stale card with the facts ([STALE] ≥30 min / [KILL] ≥90 min, the card's `agent_id`, and the suggested action). For each [STALE] line, query that agent once via `TaskOutput` using the printed agent-id: status `completed` → collect the result JSON from its output tail right there and route it into review; still `running` → keep waiting. [KILL] lines → step 3.
3. **Stall verdict at 90 min** — a `[KILL]` line from `watchdog` (or a TaskOutput probe showing no progress): mark the card `failed` (with an `error` noting "停摆判死" or the actual cause found, e.g. `insufficient_balance`), disclose it in the report, and either take over the work from the main session or wait for the user. Never block the whole run on a dead builder.

These rules are also mirrored in `commands/swarm.md` step 5.

## Models

**Models are not configured by the plugin.** ZCode Settings → 子智能体 (Subagents) → ZCode Swarm gives each of the five roles its own model: planner, architect, builder, reviewer, fixer. Stored by the host in `~/.zcode/v2/agents-state.json` (`pluginAgentModelSelectionOverrides`) and applied to the agent profile's `modelSelection`, outranking anything the plugin could say. A role without an entry = 继承默认, i.e. it follows the main session's model.

Run `node <swarm-config.mjs> show --json` before starting and read the `roles` array: each entry is `{ role, model, source }`, where `source` is `宿主设置` (host setting) or `继承默认` (inherit). Write that array into the ledger init as `agent_models.resolved`, and pass `settings.rework_rounds` as `rework_rounds` — `show` is the only place the rework cap comes from. The report card's role-model table then renders from the ledger.

Do not try to choose a model at dispatch time: the Agent tool has no per-spawn model parameter, and the host's per-agent setting wins anyway. Never edit the shared agent files' `modelSelection` to route a model. When the user names a model ("这次用 kimi"), tell them it is set in ZCode Settings → 子智能体 → ZCode Swarm for the role; then re-read `show --json` so the ledger reflects it.

## Ledger discipline

`.swarm/ledger.json` is the single source of truth for the run. Every state change — dispatch (`working`), result intake (`reviewing`), verdict (`passed`/`failed`), rework round, expansion (`spawn`), bounce, findings, gate outcome, fixer rounds, `finish` — is written to the ledger **before** the next orchestration step runs; the board and the report are always generated from the ledger (`render board` / `render report`), never from the main session's memory. If the session is interrupted, the ledger is what makes the run auditable or resumable (`/swarm resume`) — never delete or hand-edit it while the run is live.

## Split discipline (kept from v1)

- **Read-only evidence.** A card's scope comes from files/dirs the requirement names, or from a dependency boundary you confirmed yourself with Read/Grep/Glob. No evidence → `scope: ""` (unlimited) plus a note; never invent scopes.
- **Non-overlapping.** Two cards' scopes must not be equal or in a parent/child relation (case- and slash-direction-insensitive). Cannot separate them → merge into one card; fewer over colliding. One writer per file — two cards that touch the same files are one card; read-only work needs no scope.
- **Honest count.** Cannot produce ≥2 cards → say "this is not a swarm", use one Agent.
- **Coarse over complete.** A few minutes, not a deep dive: obvious scopes directly; uncertain ones stay coarse — expansion backfills related work discovered mid-run.
- **Role per card.** builder for implementation cards, reviewer for read-only checks; role names drive the report's model table. Never assign a model to a card — the host decides it per role.
- **Quality line.** Builders and reviewers never get to ask questions: a card that needs "confirming later" is a bad card — bake the criteria into `acceptance`.

## Key differences from v1

| | v1 (engine) | v2 (independent) |
|---|---|---|
| Orchestration | Saved workflow engine (TypeScript) | Main session orchestrates directly with the Agent tool — nothing to launch. The saved workflow (`~/.zcode/workflows/zcode-swarm-<key-hash>.dwf.ts`) still exists as a deploy artifact and is re-rendered on settings save, but `ensure` (SessionStart hook / `validate`) only keeps it in sync and the v2 flow never reads it |
| Checkpoints | Model-confirmation card + run-approval dialog | Zero by default — the only user touchpoints are the requirement and the final report |
| Model limits | Compile-time literals checked across every configured model (v1) | No model configuration in the plugin — each role's model is a host per-agent setting (Settings → Subagents → ZCode Swarm), inherit when unset. `show --json` reads the resolved `{role, model, source}` list, which goes into the ledger as `agent_models`; nothing is checked or healed before start |
| Ownership | Workflow script owns the loop, journal-backed | Main session owns the loop — split → dispatch → review → rework → expand → gate → fix → report, event-driven on background-completion notifications, with the ledger as the only state |
| Design stage | N/A | Optional architect agent for cross-card consistency |
| Board | Artifact board inside the workflow tool | Chat-stream Gen UI cards (`render board`) **plus** a persistent side panel since 0.4.2 — plugin `ui.surfaces` registration; the `swarm_board` MCP tool returns a compact run summary (full data via `resources/read ui://zcode-swarm/board.json`; the panel itself opens from the sidebar icon), the server `fs.watch`es the ledger and pushes `ui://zcode-swarm/board.json` updates (panel subscribes + 5s fallback poll, 2.5s direct-read poll, static snapshot as last resort). Both views share the ledger, the panel never replaces the cards |
