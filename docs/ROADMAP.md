# zcode-swarm 总蓝图：架构与路线

> 2026-11-08 定稿。愿景判据 → 架构 → 里程碑 → 硬限制 → 纪律，一页看全。
> 下图的历史骨架来自 v1（工作流引擎），保留作历史：0.4.0 起进入 **v2.0 独立编排**，执行层由「ZCode 内置动态工作流」换成**主会话直接编排 Agent 工具**，编排协议与持久状态仍由本插件提供；引擎产物（workflows/*.dwf.ts 渲染链）仅留作部署用途，不再是开工入口，也不能拿旧工作流名当启动入口。图中「六列看板(工具内)」「施工报告(primary)」「质量门里的 git 越界检测/审查员改动指纹」等 v1 机制描述均属历史；0.4.2 现役呈现＝聊天流 Gen UI 卡片 + 侧栏常驻面板「团队看板」（插件 `ui.surfaces` 注册，`swarm_board` MCP 工具唤起，见里程碑 0.4.2 行），审查禁改靠 agent 工具集 + 纪律（无自动指纹检测）。**模型自 0.4.2 起完全由宿主「子智能体」设置决定（ZCode 设置 → 子智能体 → ZCode Swarm），插件不再配置模型。**

## 一、愿景（最高判据）

**蜂群式团队开发：用户只管需求进、成品出。** 代理集体出动、自己协调，加快开发进度。拍板点随信任建立逐步收敛（三 → 二），一切中间检查点都是临时妥协而非目标形态。

## 五、平台硬限制（设计绕行，不改引擎）

1. worker 不能再造 worker——恒两层，按需造人只发生在脚本/主会话侧
2. worker 互不可见——协调只能经脚本中转（同时是防串台特性）
3. 子代理工具集相同——审查禁改＝提示 + agent 定义不挂 Write/Edit（Bash 仍可写，靠纪律兜底）；v1 另有 git 改动指纹作第二道保险，v2 没有自动指纹检测
4. 工作流只能显式触发 + 确认窗口——2026-11-14 在 Full access(yolo) 下实测**仍需点击**：平台硬底线，权限模式绕不过；M4 按一键放行档设计（v1 引擎路径；v2 改走主会话编排，无此确认窗）
5. 模型名单须启动前字面量——运行中加模型要 Amend；启动时引擎检查**全部**字面量，任何一个解析不了整个团队都起不来（**v1 引擎路径的历史约束**；v2 无引擎、插件也不再配置模型，每个角色的模型由宿主「子智能体」设置决定，没设＝继承默认跟随主会话，因此不存在"名单解析失败起不来"这回事）
6. 裸模型名只在会话供应商里解析——**这是 v1 的历史约束**：v1 名单只收完整 id 或 inherit（跟随会话），开工前用 ListModels 预检；**v2 已无插件名单、无预检**，模型写法由宿主设置界面校验。启动失败禁止即兴复制/手改脚本（0.3.3 起的硬规矩，起因见下）
7. 未跟踪文件的内容改动检测不到——每次报告披露

> 0.3.3 起因（2026-11-09 实测）：默认名单是裸名 `GLM-5.3-Flash` 等，在 magpie 供应商的会话里按名启动失败；主代理即兴复制脚本、手改成 `magpie/zcode/…`、为此加载 dynamic-workflows 技能后才从 path 启动——绕过了用户设置，也是"启动前要等十几分钟"的一部分来源。另：升级时删掉旧缓存目录会让仍在运行的会话报 `Skill not found`，部署须保留上一版本目录。

## 六、纪律

- **版本**：次版本位及以上升级须用户确认；小改动补丁位；未公开编号可回收；连续递增（当前 **0.4.3**）
- **Git**：本地随时可提交；push GitHub 由用户决定（当前 0.2.0 为最新公开版）
- **设置**：**模型由宿主「子智能体」设置决定**——ZCode 设置 → 子智能体 → ZCode Swarm，给 planner / architect / builder / reviewer / fixer 分别指定模型（落盘 `~/.zcode/v2/agents-state.json` 的 `pluginAgentModelSelectionOverrides`）；没设的角色＝「继承默认」，跟随主会话模型。**插件不配置模型**，也没有模型名单、设置卡片、预检自愈或按次点名这类入口。插件侧只剩返工轮数（宿主插件配置 `reworkRounds` 只读，或 `set` / `reset` 存到当前项目），`show`（`--json` 含 `roles` 数组：每角色实际模型与来源）可随时查看实际生效值
- **部署**：新版本装进 `cache/<新版本>/`，上一版本目录保留到下次升级，避免运行中的会话找不到技能；部署须带秒级备份与 REMOVED 清单（仓库本身只有 `publish/` 里的历史 zip，不含部署脚本）。**in-place 部署后须重渲染 saved workflow（或由 ensure 自愈）**：`~/.zcode/workflows/zcode-swarm-<键哈希>.dwf.ts`（外加 default 兜底 `zcode-swarm.dwf.ts`）是按模板 + 设置生成的部署产物，脚本换了而工作流没换，会让工具链上的验证与实际脚本漂移；`swarm-config.mjs ensure`（SessionStart 钩子与 `validate` 都会跑）按「当前模板 + 当前设置」应有的渲染结果做内容比对，不一致就重写并打印原因，一致才输出「已是最新」。**渲染链内的 bounce / 模型相关实现属历史路径**：`workflows/*.dwf.ts` 自带一套独立的 `bounceBatches` / `MAX_BOUNCE_BATCHES`（每卡 2 批）等逻辑，与 `scripts/swarm-ledger.mjs` 的 `MAX_BOUNCE_BATCHES = 2` 是两套互不相干的实现；v2 编排（主会话直接编排 Agent 工具）不执行渲染链，故两侧口径**不需要对齐**，数值或行为不一致不是 bug，不要为「同步」去改渲染链或 ledger
- **闸门成本序（S1）**：任何校验闸门必须排在比它便宜的步骤之后、比它贵的步骤之前（`show` 秒 → validate 秒 → 拆单分钟 → 派工）；新闸门照此排序
- **脚本强制优先（S2）**：宿主硬规则（Gen UI 根目录、宿主设置只读、任务卡字段/范围校验）一律在脚本侧生成时校验、报错自带修复命令；文档只留判断类指引；每次踩到宿主限制先问"能否变成脚本检查"
- **仓库自验证（S3）**：`node test/run.mjs` 全绿才可提交/部署（缺 Chrome/TypeScript 的环境允许 SKIP 但要显式打印）；每个线上事故必须落成一条回归用例
- **验证分级（S6）**：结论标证据类型（typecheck / 无头 / 真实运行）；未验证项进台账当显式待办，不得对外表述为已完成
